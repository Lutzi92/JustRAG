# JustRAG

Go-first RAG application with a React frontend, PostgreSQL + pgvector, Redis, and Asynq workers.

## Quick reference

**Site_config flag namespaces** (admin Agent panel; long-form mechanism docs in `docs/retrieval.md` and `docs/agent-orchestration.md`):

- `chat_*` — chat orchestrators, gates, post-response
- `chat_answer_history_*`, `chat_transform_followup_enabled` — answer-time conversation history (the answer LLM was single-turn until 2026-06) + retrieval-free reformat follow-ups ("das als Tabelle"); both **default ON** (correctness fixes; the keys are kill switches)
- `chat_date_awareness_enabled` (default **ON**, kill switch) — injects the current date (`chat_date_timezone`, default `Europe/Berlin`) into the answer system prompt so the LLM resolves "today"/"yesterday"/"since May". `chat_date_tools_enabled` (default off) + `chat_date_tools_max_results` (default 50) enable the `recent_documents` MCP tool (list files added in a date window). `kb_search` also accepts optional `date_from`/`date_to` (always available). Date windows key on the effective date `COALESCE(published_at, created_at)` — the single `effectiveDateExpr` in `internal/vector/recency_boost.go`, mirrored byte-identically in `internal/mcp/builtin/recent_documents.go` (a source-text drift test in each package pins it). `files.published_at` (mig **0071**) is filled by the three origins that carry a content date — RSS (the item's `PublishedParsed`), Confluence **pages** (the page version timestamp; attachments stay NULL) and git (the HEAD commit's committer time, shared by every file of that shallow-clone sync) — always through the one clamp `files.ClampPublishedAt` (a future date becomes `now`; nil stays nil). Uploads, the crawler and every other origin leave it NULL and key on `created_at` (ingest time), and there is **no backfill**, so files ingested before 0071 — and Confluence/git files not re-synced since — do too. `chat_recency_listing_enabled` (default **ON**, kill switch; + `_window_days` 7, `_max_results` 50, `_name_match_enabled` ON) — deterministic path for "Welche neuen Meldungen gibt es?"-style queries: `IsRecencyListingQuery` window-scopes retrieval via `SearchOptions.CreatedAfter` and injects the complete file listing for the window as a system-prompt addendum (semantic retrieval alone returns an arbitrary subset for content-free recency queries; the listing supersedes the enumeration pre-pass). The name-match arm additionally includes files whose NAME carries a word-boundary "neu"/"new" label (CERT advisories: NEU vs UPDATE) even outside the window — when the query says "neu"/"new", no user file selection exists, and the window listing isn't truncated, retrieval switches from CreatedAfter to an explicit FileIDs union so those stay citable. Standard `PrepareChatContext` path only. `internal/chat/date_prompt.go`, `internal/chat/recency_listing.go`, `internal/mcp/builtin/recent_documents.go`.
- `chat_longmem_*` — per-user long-term memory (incl. `_recall_semantic`, `_conflict_*` for ANN + Mem0 conflict resolution)
- `chat_longcontext_*` — System-2 long-context routing for global-synthesis queries. **Since Wave 3 an orchestrator** (`OrchLongContext`, `internal/chat/longcontext_chat.go`) sitting directly below DRIFT and above Supervisor: before that the route was a branch inside `PrepareChatContext`, which streaming `complex_reasoning` turns never reach (they all go through `tryDeepChat`), so it was configured, documented, metered and unreachable for exactly the query class it targets. Gate `chat_longcontext_enabled` (default off) + `complex_reasoning` + `IsGlobalSynthesisQuery`; `chat_longcontext_max_tokens` + `chat_longcontext_top_k` (200) size the wide pool. `chat_longcontext_mode` (`flat` | `map_reduce`, default **`map_reduce`** since Wave 5, per-KB) picks the consumer (`internal/chat/longcontext_consume.go`, shared by the orchestrator and the `PrepareChatContext` branch): `flat` hands the token-budgeted pool to the answer LLM raw (byte-identical to the pre-Wave-3 prompt tail), `map_reduce` groups it in score order into `chat_longcontext_map_group_size` (8, [2,32]) chunk groups, extracts `{source_idx, claim, quote}` findings with one fast-tier call per group (`chat_longcontext_map_model`, up to `chat_longcontext_map_concurrency` (6, [1,32]) in flight, 45 s per group under a 180 s whole-stage deadline) and answers from the findings plus bare source headers. **Wave 3 kept `flat`** — Task-4 judge A/B on `eval/golden/global-synthesis-de.jsonl` (12 DE questions, gitignored; acceptance record `eval/golden/global-synthesis-de.acceptance.md`): answer relevance saturated (1.000 on all three runs, so the decision rule's primary arm was unsatisfiable), faithfulness flat 0.613 / map_reduce 0.565 / flat-repeat 0.597 (inside the ≈0.14 SE of a 12-question mean), and the only noise-exceeding effect was context precision 0.409 → 0.600 (**+19.1 pp**) — bought with 63.4 s vs 10.2 s of context assembly per question and 25 extra fast-tier calls per turn. **Re-measured in Wave 4** with the two instruments built for it (coverage judge over `expected_points`, position-debiased pairwise judge) — four judged runs (flat ×2, map_reduce ×2) plus three pairwise comparisons, acceptance record §2: `map_reduce` won **16 of 20 pooled decisive pairs** (0.800, Wilson [0.584, 0.919]) and raised mean coverage in both cross pairs (+6.94 pp and +2.78 pp against a 1.67 pp same-flag band), but the **pre-registered per-pair rule (W4-R7) failed**: pair 1's Wilson lower bound is 0.434 < 0.50 at n=12 questions (8 of 11 decisive; 9 were needed). So Wave 4 left it opt-in: the pooled read was not pre-registered and the set was under-powered at that size; cost was 1.65× wall time (938 s vs 570 s per 12 questions). **Decided in Wave 5 (W5-R1): the default is now `map_reduce`.** The rule was re-registered on the POOLED decisive cross pairs on 2026-09-06, before the extended set was authored, and the set was grown to **24** questions (acceptance record §4): map_reduce won **34 of 36 pooled decisive pairs** (0.944, Wilson lower bound **0.819** > 0.50), pooled coverage 0.5837 vs flat 0.5333 (**+5.03 pp** against a 1.39 pp flat-vs-flat band), and the flat-vs-flat control landed at **0.364**, inside the required [0.35, 0.65] window — all four criteria passed. Cost is reported, never a veto: **1.28× wall time** (1797 s vs 1401 s per 24 questions), i.e. the 25 extra fast-tier calls per turn are unchanged. Faithfulness came out marginally *lower* for map_reduce (0.461/0.533 vs 0.464/0.569) and answer relevance is saturated at 1.0 — both diagnostic, neither a decision input. The **unset key** now reads `map_reduce`; an **unrecognised** value still normalises to `flat` and logs a warning, so a typo can never buy the expensive mode. Pin the old behaviour with an explicit `chat_longcontext_mode = flat`. The route itself is still gated by `chat_longcontext_enabled` (default off), so no deployment changes behaviour without also turning long-context on. `map_reduce` ships opt-in and is **skipped on abstain** in `PrepareChatContext` (like ECoRAG compression / multipass / the sufficient-context gate). Fail-soft: a failed or panicking group contributes its chunks' first 600 runes as findings, an all-empty map degrades to `flat`. Trajectory `longcontext_route` / `longcontext_map` / `longcontext_reduce`; metric `rag_longcontext_route_total{outcome,mode}` — **the label set gained `mode`, and `outcome` gained `considered` (gate on, eligible turn, classifier did not fire) and `map_empty`, so dashboards/alerts keyed on the old label set break**; an orchestrator error that falls back to `PrepareChatContext` can count the same turn twice.
- `chat_context_compression_*` — ECoRAG evidentiality-based post-rerank filtering
- `chat_sufficient_context_*` — holistic "does the assembled set suffice?" abstention gate (standard + supervisor paths)
- `chat_citation_spans_*` — span-verified citations (Wave 3): after the deterministic citation validator has run, one fast-tier call copies one verbatim quote per still-eligible citation, matches it exactly (NFC + lower-case + whitespace-collapse normalised, quote edges trimmed) against the cited source body and, on a match, upgrades that entry to `method: "span"` with `span: {start, end}` **rune** offsets into `sources[n-1].content`; the FE popover highlights the quote and falls back to the plain snippet on a malformed span. `_enabled` default **off** (opt-in; requires `citation_validation_enabled`, the pass it extends), `_max_sources` 12 [1–50], `_timeout_ms` 8000 [1000–60000], `_model` fast-tier — **no admin-UI control for `_model`**, it resolves through `model_tier_fast` like every other `*_model` key. Summary / community-summary sources are excluded from the extraction. No migration (the `verification` JSONB gains an optional key). `internal/chat/citation_spans_verify.go`, `internal/prompts/citation_spans.go`.
- `chat_conflict_*` — conflict / supersession surfacing (Wave 5, default **OFF**, per-KB). After the final chunk set is assembled — on the standard `PrepareChatContext` path AND on the Supervisor path, mirroring the tabular router's dual wiring, right after that router and skipped when the turn is already abstaining — one structured fast-tier call compares the turn's own numbered sources and reports pairs that contradict each other or supersede one another, deciding direction from each source's date line alone. Gate `chat_conflict_surfacing_enabled` (false) + at least **2 distinct files** in the *capped* list; `chat_conflict_model` (fast-tier chain), `chat_conflict_max_chunks` 12 [2–30], `chat_conflict_timeout_ms` 6000 [1000–30000] (timeout ⇒ no addendum, no badge, a trajectory event). Output is **one wire shape everywhere** — `conflicts` is the BARE ARRAY of `{claim, sourceA, sourceB, kind: contradiction|superseded, newer: a|b|unknown, fileA, fileB}` on the SSE frame (immediately after `sources`), on the non-streaming body, in `messages.conflicts` (JSONB, mig **0072**) and on reload; the key is **omitted** when empty, so "absent means nothing to report" holds on every surface. FE: a badge next to the confidence chip with a details popover. Trajectory `conflict_surfacing`; metric `rag_conflict_surfacing_total{outcome}` (`found|none|skipped_single_file|timeout|error` — `none` exists so the flag rate has a denominator). `internal/publicapi`, `internal/openaicompat` and `internal/mcpserver` reach `PrepareChatContext` too, so with the flag on they get the **addendum only** — no frame, no persisted blob. **Measured (Wave 5, `eval/golden/cert-recency-de.acceptance.md` § "Conflict surfacing (Wave 5)"), both gates failed, so there is no recipe recommendation and no default flip:** the 8 CERT NEU/UPDATE pair questions scored **0/8** — but that is a fixture property, not evidence against the mechanism, because MMR near-duplicate suppression never assembles both halves of the queried pair (the same limitation the Wave-2 section of that file already recorded). On the pairs the detector actually saw, **12 of 37 opportunities** were flagged with direction correct **12/12** and **zero invented pairs**. The PPM false-positive rate is **0.124** (11/89 turns), above the ≤ 0.10 gate. Latency +631 ms / +268 ms per turn across two runs; retrieval metrics are identical on/off to three decimals (the pass is strictly post-retrieval). **Re-measured in Wave 6** after the CERT pair questions were rewritten to name the advisory and ask for the NEU→UPDATE delta (`must_cite_file_names` now lists both halves): at the default cap, each pair's non-cited half IS present in the assembled 30-chunk pool but sits at score rank ≈15 — outside the detector's `chat_conflict_max_chunks` window — so 0/8 pairs flag; forcing the cap to its clamp maximum (`chat_conflict_max_chunks=30` via `cmd/eval --chat-overlay`) makes all 8/8 flag with the correct `newer` direction, but the PPM false-positive rate roughly triples (**0.281/0.303** vs 0.112/0.101 at cap 12, two runs each). **No recipe recommendation at any cap; default stays OFF and `chat_conflict_max_chunks` stays 12.** `internal/publicapi` and `internal/openaicompat` now thread `FileDates` into `ChatContextParams` too (W6-R2), but both surfaces deliberately run `PrepareChatContext` with a nil site-config reader (only the degenerate-run-guard limit is read there), so `chat_conflict_surfacing_enabled` always reads false on those two regardless of the per-KB setting — `FileDates` is wired for uniformity, not yet load-bearing. `internal/mcpserver` passes a real site-config reader, so `FileDates` IS load-bearing there once the flag is on for a KB. Records: `eval/golden/cert-recency-de.acceptance.md` §§ "Conflict surfacing re-measured (Wave 6)" and "… at `chat_conflict_max_chunks` = 30". `internal/chat/conflicts.go`, `internal/ai/source_conflicts.go`, `internal/prompts/conflicts.go`.
- `chat_orchestrator_policy` (Wave 6, **GLOBAL-ONLY**, default `[]` — the ladder is byte-identical when empty, W6-R10) — an ordered table of routing rules `{when: {query_type?, global_synthesis?, enumeration?, recency_listing?, has_file_selection?, history_turns_gte?, kb_ids?}, orchestrator: drift|longcontext|supervisor|plan_execute|plan_execute_dag|agentic|standard, mode: force|prefer}`, evaluated in `SelectOrchestratorWithPolicy` after the three always-first arms (comparison, team, corpus-table — a rule can never hijack those, W6-R16) and before the flag ladder, so — unlike the ladder itself — a matching rule can route ANY query type, not only `complex_reasoning`. `force` selects the named orchestrator regardless of its feature flag; `prefer` selects it only if the flag is on, else falls through to the ladder. `standard` names the ladder's own no-orchestrator outcome (legacy deep chat / `RunDeepChat` on a turn the complexity classifier already marked complex, `PrepareChatContext` otherwise — `standard` is explicitly excluded from `opensDeepChatDispatch()`, so a `force standard` rule does **not** widen the deep-chat dispatch gate at all; its rule index is recorded on the standard path instead, via `standardPathPolicyRule`, and it never pushes a complex turn off `RunDeepChat` onto `PrepareChatContext`, since the corpus-table arm is resolved only inside that dispatch); `plan_execute_dag` pins `OrchPlanExecute` with the DAG forced on for the turn. A forced orchestrator whose dependencies are missing falls through the existing orchestrator-error → `PrepareChatContext` path, logs `chat.orchestrator_policy.fallthrough`, and emits an `orchestrator_policy` trajectory event with `Decision: "fallthrough"`; the row's `policy_rule` stays NULL (the forced route did not answer). On an applied rule the trajectory event carries `PolicyRule` (the 0-based rule index, a pointer so rule 0 survives `omitempty`) and `agent_decisions.policy_rule` (migration **0073**, nullable smallint, no backfill) records it. Validated at save time by `siteconfig.ValidateGlobalValues` (`chatpolicy.ValidateOrchestratorPolicyJSON`) — unknown orchestrators/modes/`when` fields or more than 32 rules are a save-time 400, never a silently ignored policy; the reader is fail-soft on top (an unparseable stored value logs and falls back to empty). Admin Agent panel: a JSON textarea with inline validation errors and a policy-preview table (which rule each of the four canonical turns — lookup / enumeration / complex_reasoning / complex_reasoning+global_synthesis — would hit). The eval mirror (`eval.SelectOrchestrator`) evaluates the same document through `chatpolicy.Decide`; `cmd/eval --policy '<json>'` overlays it for one run without touching `site_configs`. Measured on the PPM fixture (query_type × orchestrator → recall/MRR/cost); the numbers and the recommended (documentation-only) policy live in `eval/golden/orchestrator-policy.acceptance.md` — the shipped default stays `[]`. `internal/chatpolicy`, `internal/chat/orchestrator_select.go`, `internal/chat/http_send.go` (`resolveTurnPolicy`/`shouldTryDeepChat`).
- `chat_answer_tools_by_route` (Wave 6, **GLOBAL-ONLY**, default `{}` — no restriction on any route) — maps a route (`lookup`|`enumeration`|`complex_reasoning`|`global_synthesis`) to the answer-time tool names the catalog is filtered to on that route; 14 **built-in** tool names only — remote / per-KB MCP tools cannot be route-scoped in v1 (a cross-check test pins the built-in list against the MCP registry). `global_synthesis` wins over the query type's own entry when the turn is a global-synthesis one and the document carries that key. Enforced at BOTH the catalog projection AND the `Dispatch` boundary (`routeRestrictedDispatcher`, mirroring `RestrictedDispatcher`'s existing catalog+dispatch pairing for per-agent allowlists — a prompt-injected model can still emit a call for a tool hidden from its catalog, so the catalog is a hint, not a control); `routeRestrictedDispatcher` wraps the `ToolDispatcher` interface, not the concrete `*MCPDispatcher`, so it composes structurally over an already agent-restricted dispatcher into the intersection of both allowlists, most-restrictive-wins — no production path wraps one over the other today (answer tools are off on team-authored turns, and the answer-tools call sites always start from the plain `*MCPDispatcher`), so this is a property of the design, not something a live turn currently exercises. An entry with an empty list is a real restriction ("no tools on this route"); a missing entry means "no restriction" — `Allowlist`'s `ok` return distinguishes the two. A route restriction that empties the catalog skips the answer-tools loop entirely rather than calling it with zero tools. Trajectory `answer_tools_route` (`Decision` is the route key that resolved it, or **`"unknown"`** for a turn with no classified query type). **A turn whose query type is unknown (today: a transform/reformat follow-up, which skips retrieval/classification entirely) gets NO answer tools whenever the document configures ANY route** — an unclassified turn is deliberately not a loophole around an operator's restriction, so it is treated as fully restricted, not unrestricted, the moment `chat_answer_tools_by_route` is non-empty at all. `rag.completion`'s `answer_tools_path` log field now means "the tool loop actually ran" (not merely "tools were configured/enabled") — a route restriction or the unknown-query-type case can leave `chat_answer_tools_enabled` true while this reads false; update dashboards that read it as a simple flag mirror. Validated at save time (unknown route or tool names rejected — including `code_exec`, which is a recognized built-in name but is rejected too, since `MCPDispatcher.AnswerToolCatalog` never puts it in the answer-time catalog and naming it would otherwise silently leave that route with no tools at all). **Not measured on dev** (W6-R8a — the eval harness never runs the answer-tools loop); the documented operator procedure is `SELECT mode, count(*), avg(jsonb_array_length(coalesce(tool_calls,'[]'))) … FROM agent_decisions WHERE created_at > … GROUP BY mode` before/after enabling. `internal/chat/route_tools.go`, `internal/chat/restricted_dispatcher.go`.
- `chat_answer_degenerate_run_limit` (global-only, default **400** runes, `0` disables, otherwise clamped to [50, 100000]) — a generation-layer guard, independent of orchestrator, on every answer surface. While the answer streams, the assembled text is watched for a **degenerate run**: the maximal region periodic with period p ∈ [1, 4] (a run of one repeated rune, or a repeated 2–4-rune pattern), counted continuously across chunk boundaries. When that region *exceeds* the limit the guard cancels the child context the completion runs under (the provider stops generating, and billing), stops forwarding, strips the run out of the buffered answer, appends a one-line notice in the answer language and streams exactly that as the final content frame; the turn then completes normally (message persisted, post-response tasks, `aiMessageId` + `[DONE]`). Non-streaming surfaces get the same strip + notice post hoc. Full guard on web (both streaming paths), public API and OpenAI-compat (each has its own stream loop; the tripped branch on all four goes through the single forced variant `chat.GuardStreamedAnswer`, which also streams the trip chunk's un-forwarded pre-run prefix ahead of the notice — that is what makes the client's assembled text carry every rune of the guarded answer, and hence what makes OpenAI-compat's closing-chunk citation annotations, computed over the **guarded** text, line up with what the client holds); post-hoc strip on web non-streaming and the KB-as-MCP `ask_kb`. Trajectory `answer_degenerate_guard{limit, run_length}`; metric `rag_answer_degenerate_total{surface}` (`web|api_v1|openai_compat|mcp`) — alert on any non-zero rate, the guard contains the symptom, it does not fix the model. Calibration: Wave 4's G01 emitted ~15 400 unbroken `_` in a 17 337-rune answer, while a wide Markdown table rule is ~300 — 400 sits above any realistic rule and three orders of magnitude below the failure. Reasoning tokens are deliberately **not** guarded. `publicapi`/`openaicompat` gained a site-config setter purely so `0` disables the guard there too. Takes effect on the next turn; no restart, no re-ingest. `internal/chat/degenerate_guard.go`.

- `query_cache_*`, `step_back_*`, `mmr_*`, `rerank_blend_alpha*`, `top_n_*` — retrieval pipeline (`query_cache_similarity_threshold_*` for per-query-type thresholds). `rerank_candidate_depth` (+ `_lookup`/`_enumeration`/`_complex_reasoning`, per-KB) sizes the pre-rerank candidate pool; sentinel `0` = legacy `max(4×top-N, 50)` with a reranker / `max(2×top-N, 30)` without, returned uncapped exactly as before this knob existed. - `bm25_simple_arm_enabled` — second unstemmed tsvector arm (recovers terms the stemmer destroys); `bm25_tiered_boost_enabled` (default off, **deprecated 2026-09** — the A/B regressed every route beyond the noise band under `ts_rank` and added nothing under `bm25`; frozen, do not enable, removal is a later release) — coarse ts_rank×100/×10 IDF proxy. `bm25_scoring_mode` (`ts_rank` | `bm25`, default `ts_rank`, per-KB) selects the keyword arm's ranking formula: `ts_rank` is Postgres's built-in two-argument `ts_rank()` (term frequency only, no IDF, default normalisation 0 — no document-length or cover-density/proximity weighting); `bm25` computes real Okapi BM25 (`bm25_k1` default 1.2 [0.5–3.0], `bm25_b` default 0.75 [0–1], both per-KB) from per-KB/per-dimension stats tables `bm25_kb_stats_<dim>`/`bm25_term_stats_<dim>`, which the worker's `bm25_stats_refresh` maintenance loop recomputes every 15 min (stale = no stats row, or a stats row older than the newest chunk, or older than 24h; skips KBs with an active ingestion). A KB/dimension with no stats row falls back to `ts_rank` per query and increments `rag_bm25_mode_fallback_total{reason}`; `rag_keyword_arm_mode_total{mode}` counts which mode actually ran. **Default stays `ts_rank`** — the Wave-3 retune grid (`bm25` × `rrf_weight_bm25` {0.5, 0.75, 1.0} × α {0.6, 0.8}, `eval/golden/bm25-retune.acceptance.md`) found **no winning cell**: no `bm25` cell moved lookup MRR at all against a 4.7 pp same-flag noise band. **KB permission model (four roles):** `view < edit < admin < owner`, strictly ordered. `edit` fills the corpus (upload/delete files, RSS/Confluence/git sources, crawl); `admin` decides how it is processed and answered (description/prompt/models/tuning knobs, agents/teams, eval, canonicalize, communities, member management) — the dividing line is: anything that can force a re-ingest or change answer quality system-wide is `admin`, not `edit`. **Renaming is the one field of `PATCH /api/kb/{id}` that is stricter than the route's `admin` gate**: `kbaccess.CanRename` allows only the `owner` on a private KB (superadmin resolves to owner) and only a system `admin`/`superadmin` on a public, ownerless KB — a `kb_members` `admin` row alone gets 403 on `name`. The UI mirrors it with `canRenameKb` (pencil on the Home card + workspace-header title, `KbHeaderTitle`; public KBs also keep the name field in `GlobalKbSettings`). `owner` is unique per KB (partial unique index) and moves only through the explicit transfer endpoint, never through `/members`. `kb_members(kb_id, user_id, role)` is the **sole authority**; `knowledge_bases.user_id` survives only as a trigger-maintained mirror (`kb_members_sync_owner_trg`, fires on `INSERT OR UPDATE ... WHERE role='owner'`) that ~40 pre-existing owner-display queries still join through — never write it directly. **Invite links** (`kb_invite_links`, migration 0067): a KB admin can mint permanent, revocable links that grant `view`/`edit`/`admin` on redemption (`POST /api/invites/{token}/redeem`, authenticated-only + rate-limited — the redeemer has no KB role yet, so `kbViewChain` would 403 them). Redeeming raises the caller's `kb_members` role and **never lowers it**, never touches an `owner` row, and deletes an `opted_out` `kb_subscriptions` row in the same transaction — without that last step the joiner would be a member of a KB the overview still hides from them. Revoking stops future joins only; existing members stay. Tracking is a counter plus `last_used_at`, no per-person log. Caveat: a system-role admin who redeems an invite link on a public KB writes an explicit `kb_members` row that shadows their implicit admin (rule 2 beats rule 3 below) — the never-downgrade guard compares only `kb_members.role` and cannot see effective role. Recoverable via the global-KB editor endpoint. `kbaccess.RequireKBRole(min)` is the only route gate and `kbaccess.EffectiveRole(kb, sysRole, memberRole)` the only resolution ladder (`internal/kbaccess/middleware.go`); `internal/files`, `internal/openaicompat`, and `internal/academic` call `EffectiveRole` directly for their second, handler-internal check instead of hand-rolling one. Five rules, in order — order is load-bearing (an explicit `kb_members` row must beat the implicit public-KB roles, or an editor on a public KB would be demoted to view): (1) system role `superadmin` → `owner`; (2) a `kb_members` row → that role; (3) `IsGlobal` + system role `admin` → `admin`; (4) `IsGlobal` + `IsPublished` → `view`; (5) else → 403. `knowledge_base_shares` and `global_kb_editors` are **legacy remnants** — Phase 1 (migration 0064) backfilled them into `kb_members` and left them in place (expand/contract); they are dropped only in the cleanup release that follows Phase 2 (`docs/superpowers/specs/2026-08-12-kb-rollen-und-sichtbarkeit-design.md`). Operator-visible behavior changes from Phase 1: a plain user can now reach their own KB's settings (`kbAdminChain` replaced `kbTuningChain`, dropping the extra system-role gate); **unpublished** global KBs are no longer readable by ordinary users on *any* `view`-gated route — the whole `kbViewChain` (chat, graph, studio/generated content, files, research, export) plus the `/api/v1/*` public API and the KB-as-MCP endpoint, which wrap `RequireKBRole(kbaccess.RoleView)` directly. The old `RequireKBPermission` granted `view` on any `IsGlobal` KB regardless of `IsPublished`; rule 4 now requires both (`files`, `openaicompat` and `academic` additionally repeat the check handler-internally, which is why they get named — the tightening is not limited to them).

**KB visibility model (Phase 2):** `knowledge_bases.visibility` (`private` | `public`) is the write-side truth; `is_global` survives only as a `GENERATED ALWAYS AS (visibility = 'public') STORED` column so pods from the previous image survive the rolling deploy, and it is dropped in the cleanup release — no Go code reads it. A public KB has **no owner**: publishing (`POST /api/admin/kb/{id}/publish`, system admin, offered per row in the admin KB-Übersicht) demotes the owner's `kb_members` row to `admin` and NULLs `knowledge_bases.user_id` by hand, because `kb_members_sync_owner_trg` fires only `WHEN (NEW.role = 'owner')` and stays silent on a demotion. Publishing is **staged**: it also forces `is_published = false`, so the KB is public but not yet live — visible only to its KB admins (any `kb_members` row, e.g. the demoted ex-owner or a curator) and to system admins, until an operator flips the catalog toggle in the global-KB admin tab. This is a list-visibility rule, not a route-access one: `ListGlobalKnowledgeBases`'s non-admin overview query OR's a `kb_members` EXISTS check ahead of, and independent of, `is_published` — that arm is what bypasses the flag for members while it stays staged. `is_published` DEFAULTs to true (migration 0012), so without that write a first publish would go world-readable instantly and a re-publish after an unpublish would land silently invisible. Unpublishing requires an explicit new owner and deletes every `kb_subscriptions` row for the KB (chats are kept — losing access is not the same as asking to be removed). Overview visibility for a public KB is **no `opted_out` row** AND (`kb_members` row (regardless of `is_published`) OR (`is_published = true` AND (`kb_subscriptions.state='subscribed'` OR `auto_subscribe`))) — an ordinary subscriber or auto-subscribe candidate never sees a staged KB, only a member does. The opt-out beats *every* arm, membership included, because the star on a Favoriten card is a pure favorites toggle: `useKbRemoval` routes every public KB to `DELETE /api/kb/{id}/subscription`, never to leave-or-delete, so it drops no membership and no chats (that is what "remove from Favoriten deleted my chats" was). To keep that reversible, `GET /api/kb/catalog` lists published public KBs **plus staged ones the caller is a member of**, and `PUT/DELETE …/subscription` accept a staged public KB (only a member reaches the view-gated route for one). `auto_subscribe` **defaults to false**, so a newly published KB is catalog-discoverable but pushed to nobody — the 0065 backfill sets it only for KBs that were global *and* published before. Because of that third arm, `kbmembers.LeaveKB` ("remove from my overview" for a member) must drop the membership, the caller's chats **and** write an `opted_out` subscription row in one transaction: deleting the subscription row instead would let `auto_subscribe` re-match and the tile would return with the chats already gone. `GET /api/kb/catalog` is the discovery surface, `kb_categories`/`kb_category_links` its filter tabs — single-select with a leftmost "Alle", read through the authentication-only `GET /api/kb-categories` (the `/api/admin/` twin 403s for ordinary users, which had made the filter invisible to exactly the people the catalog is for; system admins curate the list, any KB admin assigns their own KB). The catalog search spans `name`, `description` **and `header_text`**, and displays `COALESCE(description, header_text)`: `description` has no editor in the UI, so searching it alone matched nothing users could see. **The overview is subscription-filtered for system admins too**: `kb.Handler.ListGlobalKnowledgeBases` passes `isAdmin=false` unconditionally, because the store's admin arm (every public KB, staged or not, regardless of subscription) made the section un-curatable — an admin's "remove" click was undone by the next fetch. The store's `isAdmin` arm stays live for `internal/openaicompat`, which deliberately keeps addressing every public KB. Consequence: `adminglobalkbs.CreateGlobalKB` now enrols the creating admin as a `kb_members` `admin` row in the same transaction (`GlobalKBCreate.CreatedBy`), since a fresh public KB has no owner, no subscribers and `auto_subscribe=false` — without that row the creator would not see the KB they just made. `internal/kbvisibility`, `internal/kbsubs`, `internal/kbcategories`.

**Overview UI (`web/src/components/HomeView.tsx`):** four `KbAccordion` sections — Favoriten (public KBs, open), KBs entdecken (`KbCatalogPanel`, closed), Mit mir geteilt (closed), Meine KBs (open). Open/closed state persists per section in `localStorage`; a collapsed section is **unmounted**, which is what makes expanding "KBs entdecken" re-read the catalog so a newly published KB needs no page reload. The owned/shared split is client-side on `myRole === 'owner'` — `GET /api/kb` stays one request. `AuthenticatedApp` also refetches both lists whenever `view` returns to `'home'`, so a publish performed in the admin UI lands on the overview. All four sections render the same card; the discovery card carries a star toggle (outline = add to Favoriten, filled = remove) instead of the chips/badges, because the catalog projection has no stats to show. The discovery grid folds at **8 cards** with a "show N more" button (client-side — the request is already capped at 200 rows, so the count in the button is exact); the fold re-closes whenever the query or the category tab changes. **`GET /api/kb/{id}`** (view-gated, `kbViewChain`) exists for that panel: a not-yet-subscribed public KB is by construction absent from `GET /api/kb/global`, so opening one needs the full row fetched on click — the handler and store carry no visibility predicate of their own, `RequireKBRole(view)` is the whole access decision.

- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --judge [--judge-model <name>]` — retrieval + LLM-as-judge (faithfulness, answer relevance, context precision, plus **coverage** on rows that carry `expected_points`). Judge parsing is **tolerant** since Wave 4 (W4-R1): a score emitted as a numeric string is accepted and clamped to 1–5, and a boolean list whose length differs from the contexts/points is truncated or padded with an entry in `judge_warnings` — a sample is dropped only when the JSON is unparseable. The aggregate carries `faithfulness_n` / `answer_relevance_n` / `context_precision_n` / `coverage_n` and the printer shows `(n=…)` next to each mean (`judged_count` keeps its old meaning: questions with a Judge block). Pre-Wave-4 judge numbers stay comparable for well-formed responses — the same responses score the same — but `n` may now be higher, because samples that used to be dropped are kept. Since Wave 6 (W6-R4/R17), a decoder failure (a brace-balanced-but-invalid object — a raw newline, an unescaped quote, or a trailing comma inside a string; not truncation, not fences) triggers exactly **one** bounded retry, localized to the question's language, with the decoder's own error appended to the prompt; every attempted retry — success or failure — is recorded in `judge_warnings` as `retry:<metric>` and increments `rag_judge_retry_total{judge}` (shared by `cmd/eval`, the in-app/scheduled runner and the runtime RAGAS sampler, since all three call `internal/eval.Judge`). The parser itself stays strict — this is a bounded retry, not a tolerance loosening. Measured on the 24-question global-synthesis set: **0 retries, 0 remaining failures** (baseline: 2 decoder failures in 384 judge calls across the Wave 4/5 runs); the one `judge_errors` entry on that run was a transport timeout, which correctly never enters the retry path. **Comparability caveat:** the same Wave-6 change also edited the JSON-hygiene line in all four judge system prompts (`internal/prompts/eval_judge.go`), so judge scores from Wave 6 onward are not strictly byte-comparable to pre-Wave-6 numbers — including the Wave 4/5 flat/map_reduce judged runs and the pairwise records that decided the `chat_longcontext_mode = map_reduce` default; only the retry/failure counts above are a like-for-like comparison.
- `cd go-backend && ./cmd/eval/eval --pairwise-a A.json --pairwise-b B.json [--pairwise-out out.json] [--judge-model <name>]` — offline, position-debiased **pairwise preference judge** over two existing `--judge` reports (W4-R4): every question pair is judged in both orders and counts only when both orders agree, otherwise it is a tie. Prints wins/ties/losses from A's perspective, win rate with a 95 % Wilson interval (ties excluded), tie rate, and per-route + per-question tables; skipped/error pairs are counted and visible. Exit 0 (it is a measurement, not a gate), 2 on usage error. Both reports' questions must carry `kb_id` (the judge model resolves per KB). Optional golden field `expected_points` (≤ 12 points, ≤ 300 runes each) drives the coverage judge — absent means the judge is skipped, not scored 0. The global-synthesis set is **24** questions since Wave 5 (G01–G12 byte-identical, G13–G24 added, 6 points each), which is what made the pooled rule adequately powered.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context --team-id <uuid>` — per-team eval: every question dispatches through the real `RunTeamChat` (team must be attached + enabled on the KB; requires `--production-context`; incompatible with `--trajectory`; errors are hard per-question, never a silent standard-path fallback)
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context [--enhance …] [--hyde] [--multi-query] [--crag on|off] [--enumeration on|off] [--orchestrator-dispatch=true|false]` — eval through the production chat pipeline (CRAG, enumeration, contextual prefix, sandwich order). `--orchestrator-dispatch` defaults **true** (each question routes through the production orchestrator predicate; report records per-question `agent` + per-orchestrator aggregates); set `=false` for byte-stable diffs against pre-2026-05 retrieval-only runs, except that recency-listing-shaped questions now exercise the recency lister and window scoping, which pre-2026-09 runs did not. Since Wave 6 (Task 10), every question also carries `latency_ms` and per-question `agent.llm_calls` (a `CallCounter` wrapping every model-provider HTTP request — chat completion, streamed or unary, embedding, and rerank — for that question's whole `Search` call, classifier included); the aggregate (overall, per-route, per-orchestrator) gains `mean_latency_ms` (always printed, 0 is a valid latency) and `mean_llm_calls` (a pointer, `omitempty`, nil when no question in the bucket carried an `Agent` trace at all) — these are the cost half of the `query_type × orchestrator → recall/MRR/cost` measurement `--policy` (below) exists to produce.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --trajectory --orchestrator off|agentic|plan_execute|plan_execute_dag|supervisor|all [--judge]` — trajectory eval: per (question, orchestrator) emits the full agent decision sequence to `eval-trajectory.jsonl` + `.aggregate.json`. `--judge` adds four LLM judges (decomposition coverage, decision correctness, rewrite utility, tool-call correctness).
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --depth-buckets [--depth-buckets-min-chunks 4]` — position-aware analysis: adds a `depth_buckets` section (per-quartile relevant vs non-relevant counts, bucketed by chunkIndex/totalChunks) to surface position bias toward the start of long files. NOT a true RULER needle test.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context [--keep-raw on|off] [--bm25-mode ts_rank|bm25] [--bm25-tiered-boost on|off] [--recency-boost on|off] [--refresh-bm25-stats]` — Wave-2 ablation overrides on top of production-parity mode: each flag overlays the named site_config for this run only (no `site_configs` mutation), empty/unset reads the live value. `--refresh-bm25-stats` recomputes BM25 stats (creating the stats tables idempotently if missing) for every KB the golden set references, across every dim table with rows for that KB, before running — use it ahead of a `--bm25-mode bm25` run against a KB that hasn't had a recent stats refresh.

The live default is `map_reduce` since Wave 5, so an explicit `--longcontext-mode flat` is what a flat run needs now.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context [--conflict-surfacing on|off]` — Wave-5 overlay for `chat_conflict_surfacing_enabled` (empty = live value, no `site_configs` mutation, composes with the other chat-layer overlays). `on` makes every turn whose assembled set spans ≥ 2 distinct files run the conflict / supersession pass and records the resulting bare array per question as `conflicts` in the JSON report — the same value a chat turn persists and streams. Effective on the standard path and, under `--orchestrator-dispatch`, on the Supervisor path. The report gains a `Conflict surfacing:` block only when at least one question carries an entry, so a flag-off report stays byte-stable. `cmd/eval` wires a `FileDateLookup` of its own (`eval.WithFileDates`) — without one every date line reads "unknown" and the detector is instructed not to guess a direction, which would make the supersession measurement vacuous.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context --orchestrator-dispatch=true --policy '<json>'` — Wave-6 (W6-R6/R7) per-run overlay for `chat_orchestrator_policy`, validated by the same `chatpolicy.ValidateOrchestratorPolicyJSON` the save path uses BEFORE the run (an invalid document is a usage error, exit 2, never a silently ignored flag); each question's report gains `agent.policy_rule` and the human summary an `Orchestrator policy:` block whenever at least one question carried a rule. `--chat-overlay key=value` (repeatable, W6-R18) is the generic escape hatch for any OTHER chat-layer `site_config` key the same reader serves (e.g. `chat_conflict_max_chunks`); `--chat-overlay chat_orchestrator_policy=…` is rejected — use `--policy`, which validates. Both compose with the other chat-layer overlays (`--longcontext*`, `--conflict-surfacing`) through the one shared overlay wrapper; empty = live site_config.
- `cd go-backend && ./cmd/eval/eval [--pairwise-out pooled.json] --pairwise-pool a.json b.json` — pools two pairwise results over their **decisive** pairs (ties excluded from every denominator, as in `--pairwise-a/-b`), recomputing rather than averaging the two win rates, and prints Wilson bounds from **both** perspectives (they reflect, they do not swap). **Flag ordering is load-bearing:** Go's `flag` package stops parsing at the first positional argument, so `--pairwise-out` must come BEFORE the two paths; a trailing flag is rejected with an explanation rather than silently writing nothing. The inputs must put the same configuration on side A — the command warns but cannot check, since a pairwise JSON carries no report paths. A file without a `pairs` key is refused, so handing it an eval report cannot silently read as "0 decisive pairs". Exit 0 on a completed pooling, 2 on a usage error.

## Releases

SemVer `0.x` via **annotated git tags** (`v0.1.0`); the tag is the only source
of truth. Pre-1.0: **minor** = features *and* breaking changes, **patch** =
fixes only (no migration, no changed `site_config` default, no re-ingest).
`v1.0.0` is reserved for the first public release. Independent of the API
version — `/api/v1/*`, OpenAI-compat, MCP, and the ILIAS shim stay `v1`.

- **CI:** `main` → `:edge` + `:<sha>`; tag `v*` → `:vX.Y.Z` + `:vX.Y` +
  `:stable` (prerelease tags like `v0.2.0-rc.1` deliberately do **not** move
  `:stable`, since it is the unpinned-compose default). **`:latest` is not
  published** — it was how prod drifted. What suppresses it is
  `flavor: latest=false` on the metadata step; `docker/metadata-action`
  defaults to `latest=auto` and generates `:latest` for `type=semver` by
  itself, so omitting it from `tags:` is not sufficient. Do not remove it.
- **`GET /version`** reports `git describe --tags --always` (`v0.1.0`, or
  `v0.1.0-12-gabc1234` on a main build), stamped in via `BUILD_VERSION`.
- **Pinning:** compose files interpolate `${JUSTRAG_VERSION:-stable}`; k8s
  worker manifests take a literal `:vX.Y.Z` + `imagePullPolicy: IfNotPresent`.
  The `go-server` Deployment lives outside this repo and is pinned manually.
- **`CHANGELOG.md`** is generated by git-cliff (`cliff.toml`) plus a
  hand-written `⚠ Upgrade notes` block per release (migrations, flipped flag
  defaults, re-ingest requirements).
- **Migrations on deploy:** compose applies them automatically (the `migrate`
  one-shot service + `service_completed_successfully` gates). **k8s does
  not** — there is no migrate Job and neither binary self-migrates, so the
  runbook's `kubectl run … /app/migrate` step is mandatory before
  `kubectl apply`.
- **A release whose upgrade notes list a migration has no one-step rollback**
  — `cmd/migrate` is up-only.

Full procedure: `docs/runbooks/release.md`.

## Local dev setup

Required env vars (load via `.env`; docker compose reads it via `env_file`):

- **Postgres (main):** `DB_HOST`, `DB_PORT` (default 5432), `DB_USER`, `DB_PASSWORD`, `DB_NAME`
- **Postgres (vector):** `VECTOR_DB_HOST` etc. (defaults to `DB_*` when unset — single-DB setups work out of the box)

See the Structured spreadsheet Q&A recipe in `docs/feature-recipes.md` for the SELECT-grant prerequisite.
- **Redis:** `REDIS_HOST`, `REDIS_PORT`, optional `REDIS_PASSWORD`. Non-compose deployments (k8s, managed Redis) must replicate the compose files' `--maxmemory <size> --maxmemory-policy volatile-lru`: the embedding cache is bounded only by per-entry TTL + eviction, so without a maxmemory policy it grows until Redis OOMs. Keep `volatile-lru` specifically — `allkeys-lru` risks silent Asynq task loss, `noeviction` breaks task-lease renewal (rationale comment in `docker-compose.yml`).
- **Auth:** `JWT_SECRET` (required at startup, ≥32 chars; a low-entropy secret — fewer than 3 character classes — logs a startup WARN). `ALLOWED_ORIGINS` (comma-list) is **required in production** — startup fails if unset, because an empty CORS allowlist makes `rs/cors` reflect any origin with credentials. Set it explicitly on staging/UAT too: the localhost fallback (`http://localhost:5173`, `http://localhost:3000`) applies whenever `GO_ENV != production` (`NODE_ENV` is a deprecated fallback), so a shared non-prod host without it silently rejects every real origin. `AUTH_PROVIDER_SECRET_KEY` (base64 32 bytes) encrypts auth-provider secrets at rest — OIDC `client_secret` **and** LDAP `bindCredentials`; required once any OIDC row exists or any LDAP provider is saved with bind credentials (legacy plaintext rows keep working at login until re-saved).

- **Tracing (opt-in):** `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_HEADERS`

## Model tier resolution

Cost-optimization knob orthogonal to the feature recipes above. Each fast-tier task (CRAG grader, KG extractor, contextual enricher, factuality verifier, Self-RAG verifier, DAG critic, longmem extractor, KB router, RAPTOR summariser, **query decomposer (T1-1), longmem conflict classifier (T1-3), evidentiality classifier (T2-3), HyPE question generator, golden-set question generator, DRIFT follow-up generator**) resolves its model in this chain (first non-empty wins):

1. The task's per-task site_config key (e.g. `crag_grader_model`, `kg_extraction_model`, `query_decompose_model`, `chat_longmem_conflict_model`, `chat_context_compression_model`, `hype_model`, `chat_drift_model`)
2. `model_tier_fast` — deployment-wide fast-tier default
3. The KB's default chat model (legacy fallback)

Helper: `chat.ResolveFastTierModel(ctx, reader, perTaskKey)` — the single resolution function, callable from any package with a `SiteConfigReader`. Reasoning-heavy tasks (answer generation, plan decomposition, refine path) intentionally bypass this chain and use the KB chat model directly.

## Current Runtime Notes

- Data Explorer routes exist in the Go server but currently return `501`
- the default deployment is Go-only
- **OpenAI-compat source attribution** (not flag-gated, always on): `POST /openai/v1/chat/completions` returns retrieved chunks two ways — `message.annotations[]` (OpenAI `file_citation` shape, one per `[n]` marker occurrence, `index` is a **rune** offset because OpenAI defines it in characters and answers are mostly German) and `message.context.citations[]` (Azure "On Your Data" shape, carries the chunk bodies, so OpenWebUI-family clients read it natively). Streaming splits them: sources ride the **opening** chunk (retrieval finishes before the first token, so clients can render source cards immediately), annotations ride the **closing** chunk (offsets need the assembled text). Both keys are omitted rather than emitted empty, so clients branch on presence. `chat.ExtractCitationSpans` is the single definition of the `[n]` / `[1, 2, 5]` marker format — the citation validator and the annotation builder both read markers through it so they cannot drift. Caveat: this endpoint runs **no** citation validator, so annotations are model claims, not verified; out-of-range markers are dropped rather than left dangling. `internal/openaicompat/{citations,response}.go`.
- **Usage ledger** (not flag-gated, always on): `usage_events` records one row per
  **accepted** chat turn — after the KB and user resolve and the body validates,
  before the answer — on all four answering surfaces (`web`, `api_v1`,
  `openai_compat`, `mcp`). It exists because `internal/openaicompat` and
  `internal/mcpserver` persisted *nothing* (only `internal/chat/store_pg.go`
  writes chats/messages), so every message counter and every "last activity"
  timestamp was blind to API traffic while the LLM gateway still billed for it.
  One `usage.Recorder` writes it, called explicitly once per request from each
  handler — fire-and-forget on a detached context, so telemetry can never fail or
  slow a turn. Read by `internal/systemhealth` (global total + 24h, each split
  web/API), `internal/adminkboverview` (the **Aktivität** column, which replaced
  Nachrichten, plus `Letzte Aktivität`), and `internal/kb`'s `kbStatsCols`
  LATERAL (home KB cards). Every FK is `ON DELETE SET NULL`, deliberately: a
  deleted KB or user must not shrink the all-time total, which is why the global
  total can exceed the sum of the per-KB columns. Research sessions
  (`chats.type='research'`) are **not** counted, in either the backfill or the
  live path. `internal/usage`; migration 0066.

## Document parsing

Default: `pdftotext` (PDFs) + built-in DOCX/PPTX parsers (flattened tables, dropped footnotes). Spreadsheets (`.csv`/`.tsv`/`.xlsx`/`.xls`/`.ods`) parse via `parser.SpreadsheetParser` — replaces the legacy CSV/XLSX/XLS/ODS parser quartet, deliberately excludes `.xlsm` (macro-enabled workbooks, out of scope). An upload recognized as a spreadsheet is additionally gated on `tabular_max_file_bytes` (413 if over, independent of the transport-wide 500 MiB cap every upload gets — see `docs/runbooks/spreadsheet-ingest-ops.md` for the interaction between the two). It drives `internal/tabular/ingest` render-only (no Postgres materialisation, no LLM assist) when reached as a plain parser-factory entry (e.g. in-chat comparison attachments); the processor's own spreadsheet ingestion branch drives the same ingester with a real materialiser instead, per the `chat_tabular_*`/`tabular_*` Quick-reference entry above. The sheet-profiler LLM call (`ai.ProfileTableRegion`, per-region column descriptions) renders its sample grid as one JSON array of cell strings per row rather than a `" | "`-joined line, so a cell that legitimately contains that delimiter (a pasted range, a delimited list) can no longer be mistaken for a column boundary. Opt-in layout-aware parsing for the remaining document types via Docling sidecar — see `docs/observability/docling.md`. When enabled (admin Agent panel → `docling_enabled` + `docling_base_url`) and reachable, all newly ingested PDF, DOCX, and PPTX files route through Docling; failures fall back to the built-in parsers (logged with `request_id`). Every convert asks for `table_mode=accurate`, `ocr_lang` (`docling_ocr_languages`, default `de,en` — docling's RapidOCR default is English+Chinese), `do_pdf_heading_hierarchy` (heading `level` → `#` depth → `sections` metadata) and a `document_timeout`; the response's `confidence` block is logged per file (`docling.confidence`, warn on a `poor` low grade). Optional image captioning (`docling_picture_description_enabled` + `docling_picture_area_threshold` + `docling_picture_description_prompt` + `docling_picture_description_timeout_seconds`): Docling describes figures/charts with the vision model. The Go backend injects the `picture_description_api` config (endpoint + `Authorization: Bearer` + model + German value-extracting prompt + 120 s per-image timeout + a logo/icon/signature/stamp/barcode deny-list) **per-request** from the admin AI provider config — same endpoint+key the app uses, vision model = `describe_image_model` — so the model-API credential is **never** stored on the sidecar (required for authenticated model APIs); Docling only needs network reachability to the model URL **plus `DOCLING_SERVE_ENABLE_REMOTE_SERVICES=true`** — without it docling refuses to build the captioning pipeline and `FallbackParser` silently routes every PDF/DOCX/PPTX to the built-in parsers (both manifests set it; the worker probes for it at startup and logs an error). The sidecar's `DOCLING_SERVE_MAX_SYNC_WAIT` (upstream default 120 s, manifests 600) caps a sync convert independently of `DOCLING_TIMEOUT_SECONDS`. The page rebuild walks texts, tables (with their `captions[]`/`footnotes[]` refs — docling parents those to the table, not the body), and pictures (printed caption, the text docling found *inside* the figure — axis values and labels of vector charts, which docling's own markdown omits — the vision description from both the deprecated `annotations[]` and the newer `meta.description`, then footnotes), and lands each on its own page → existing chunk/embed pipeline (caption→text, no migration); reading only `md_content` is not enough, since the per-page rebuild replaces it; standalone image uploads also route through Docling (caption + OCR, Tesseract fallback). The worker converts through the task endpoints (`/v1/convert/file/async` → poll → result; sync `/v1/convert/file` only as a 404 fallback for pre-1.0 images), so the sidecar's `DOCLING_SERVE_MAX_SYNC_WAIT` no longer bounds it. Image pinned to `docling-serve:v1.32.0`; `picture_description_api` is deprecated upstream since 1.21 but its per-request replacement silently ignores the endpoint on 1.32.0 (verified live), and the preset route would put the model-API key on the sidecar, so the legacy field stays until it is removed (migration path in `docs/observability/docling.md`). GPU-contention caveat: Docling's vision calls bypass `AI_MAX_CONCURRENT_REQUESTS` — throttle by capping Docling replicas (`k8s/docling.yml` fixed replica count). `internal/parser/docling/`.

**Image description (`POST /api/describe-image`)**

```
describe_image_enabled = true                   # gate; default off (admin Agent panel → ingestion section)
describe_image_model   = <vision-capable model> # required; falls through model_tier_fast
```

| 4 | Agentic | `chat_agentic_enabled` (+ `_plateau_stop`, `_max_hops`) | Hop-1 → critique LLM → optional follow-up hops |
| 5 | Standard `PrepareChatContext` | (always-on fallback) | CRAG + enumeration pre-pass + contextual prefix + sandwich order |

**The eval ladder mirrors this one.** `internal/eval.SelectOrchestrator` (used by `cmd/eval --production-context --orchestrator-dispatch=true`) gained the **DRIFT arm in Wave 4** (W4-R3) at production's position — directly above long-context — and dispatches it through the real `chat.RunDriftChat`; the report records `agent.orchestrator = "drift"`. Comparison / Team / Corpus-table stay deliberately un-mirrored (they are explicit-intent routes, not complex-lane dispatch), documented in-code. `--trajectory --orchestrator …` is unaffected.

Per-feature index — each chat-orchestration feature (trajectory streaming, MCP tool registry, session memory, factuality verifier, refine gate, turn budget, KB router, retrieval/non-retrieval tools, tool-aware DAG planner, answer-time tool calling, KG extraction + graph_search + graph-routing modes, long-term memory + ANN recall + conflict resolution, sub-question decomposition, ECoRAG compression, long-context routing, Self-RAG verifier, iterative DAG critic, online faithfulness metric + feedback loop) with its knob, rationale, metrics, and design notes is indexed in **`docs/agent-orchestration.md`**. Enablement toggle blocks for the gated ones are in **`docs/feature-recipes.md`**.

## Observability

All HTTP requests get an `X-Request-Id` (auto-generated if absent) which is propagated through `context.Context`. Pipeline code uses `logctx.From(ctx).Info(...)` so structured logs carry `request_id`, `user_id`, `kb_id`. Background worker tasks bootstrap their own request id at task start.

Trace one request end-to-end:

```
docker compose logs go-server go-worker | jq 'select(.request_id == "<id>")'
```

Stage names emitted by the RAG pipeline: `search`, `factcheck`, `llm_completion`. Worker task lifecycle: `worker.task.start` / `worker.task.end` with `task_type` and `duration_ms`.

RAG-specific Prometheus metrics (counters + histograms) are exposed at `GET /metrics` (admin-protected) under names prefixed `rag_`. See `internal/observability/metrics.go` for the full list.

OpenTelemetry tracing is opt-in via env. Set `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (and `OTEL_EXPORTER_OTLP_TRACES_HEADERS=Authorization=Basic <base64(pk:sk)>` for self-hosted Langfuse) to emit traces with nested spans for `chat.send_message` → `rag.search` → `rag.embed`, `rag.llm_completion`, `rag.factcheck`. When the env var is unset, tracing is a no-op (zero overhead). Logs include `trace_id` + `span_id` when a span is active so logs and traces are joinable.

Per AI message, the OTel `trace_id` is persisted on the `messages` table when tracing is enabled. Admins see a "View trace" button next to each AI message that deep-links to the configured Langfuse instance (set `langfuse_base_url` in the admin Agent panel; URL pattern is `<base>/<trace_id>`).

## Research agent

The research agent stops early when `MaxConsecutiveStepsWithoutFindings` consecutive iterations add no new (non-duplicate) findings — default 2. Independent of the existing LLM-based "isComplete" judgment; deterministic guard against tangential or repetitive query plans.
